**Updated:** September 28, 2026 — **V2.14: the notice now takes the seller somewhere — and it turns out it was being delivered to a table nobody in the seller app reads.** Two things, and the second is the correction of a mistake two earlier phases made between them. *(1) The tap works.* A "your 3D model is ready" (or "…was declined") notice has carried `metadata.product_id` since V2.12 — pinned by an assertion that existed precisely because nothing read it — and now actually routes: the seller's product opens with its **actions sheet already up**, which is where the request row and the model both live. The rule is pure and table-tested (`lib/utils/model_notice.dart`), and it refuses more than it accepts: only the `models` category, only a non-blank product id, and the sheet opens **only if the product is still in the seller's catalog** — a link that fails silently is worse than one that says so, and a link that opens *somebody else's* product is worse than both. Finding it out is `linkedProduct`, a string compare against the shared seller catalog that a *cold* catalog defers rather than eats (the deep link listens to the provider instead of polling it), and the outcome the notice's product was deleted resolves to a message rather than an empty sheet. *(2) **The notice was invisible to the seller.*** V2.12 and V2.13 write to `public.notifications`, keyed to the seller's USER — which is the app's generic per-user channel, and which the seller app never renders: that feed belongs to the customer shell, while a seller's session lands in `SellerShell`, whose bell reads `public.seller_notifications`, keyed by STORE. So two phases of careful recipient work (the `profiles` join, the audit entry, eleven assertions) told exactly the right person on a channel they cannot open. Both closing RPCs now write **both** rows in the **same transaction**: the per-user notice stays, and a store-scoped `seller_notifications` row is written beside it (`type = 'model_request'`, `reference_id` = the product), so the seller sees it on the bell they already use and taps straight into the product. That needed DDL, and the DDL found a second bug: `seller_notifications_type_check` had never admitted `'new_message'`, which `SellerNotificationService.createNewMessage` has been inserting all along — the violation is swallowed by that method's `catch` as a `debugPrint`, and the live project confirms it (**39 `new_order` rows, 1 `low_stock`, zero `new_message`**), so **sellers have never once been told about a message**. The constraint now admits both. The bell insert is deliberately **unguarded**, and that claim is machine-checked rather than asserted in prose: `store_id` comes from the request row and `shoe_model_requests.store_id` is `NOT NULL`, so the recipient contract test now accepts that shape only while it parses the `CREATE TABLE` and finds the column really `NOT NULL` (with `orders.store_id` still nullable, as the non-vacuity check). **Dart coverage is 21 new tests** — 15 for the two rules (the `models`-only gate, ids that are blank or numeric or whitespace, the near-miss `'model_requests'` type, and a catalog lookup that must not match on `null.toString()`) and **5 more that read the SQL from Dart**: the keys the metadata rule reads must be the keys the migration writes, and the type the bell rule routes on must be a value the widened CHECK admits — because a type the database refuses is not a missing notification, it is a **failed close**, since the insert runs inside the transaction that answers the ask. The twenty-first is the non-vacuity test the audit's own exemption needed. **8 new pgTAP assertions** — plan 52 → 60: the constraint admits the type, the asking store's bell gets exactly one unread row pointing at the product, the *other* store's gets the decline and the reason verbatim, and **the refused decline lights nothing** (a bell row for a close that did not happen would be the worst kind of wrong, since `seller_notifications` has no status of its own to contradict it). Analyzer clean, **2,135 pass / 8 skipped**. Both SQL files have since been applied to the live project, and the flow file is **green in CI — `plan(60)`, 60/60, 2026-09-28** — so the per-file state to trust is `MIGRATIONS_LIVE_STATUS.md`.

**Prev. update:** September 28, 2026 — **V2.12: the seller is told, because a closed ask nobody hears about is the same gap one level down (P3 of the request flow).** V2.10's whole premise is that the seller *cannot* do the modelling — so leaving them to poll the product's action sheet for a week of other people's work is exactly the failure the stateful row was built to fix, just for a seller who never opens the sheet. So `fulfil_shoe_model_request` now writes the seller a notification **in the same transaction that closes the request**: `fulfilled` and `told` cannot disagree, because either both land or neither does. (The alternative — the admin screen sending it afterwards — would also be forgeable, i.e. skippable by a client that did not feel like it.) The recipient is the person who **asked** (`requested_by`), not the store owner: for this table they are the same person, and the filer stays the right recipient if that ever changes. The insert selects `FROM profiles … WHERE p.id = requested_by` on purpose, so a missing profile row yields **zero rows instead of a `23503` that would take the close down with it** — the recipient audit's rule (`docs/AI/NOTIFICATION_RECIPIENT_AUDIT.md`), reached by a join rather than a conditional, and recorded there because no contract-test pattern covers that shape. One new Postgres enum value, `'models'`, in a **file of its own** (`20260928130000`): `ALTER TYPE … ADD VALUE` cannot be *used* in the transaction that adds it, so it must sort before `20260928140000` — the same reason `20260913110000` exists for the reservation RPCs. Reusing `approval` was the alternative and it is wrong twice over: it would file a 3D asset beside an application review in every filter a seller uses, and make the two indistinguishable in their unread badges. **The Dart mirror is where the silent failure lived, which is why this phase is worth more than its SQL.** `AppNotification._parseCategory`'s default is `unpaid`, so a new SQL label with no Dart case would show the seller's model notice as **Unpaid**, with a credit-card icon, in the wrong filter and the wrong count — a bug no compiler, analyzer or widget test can see. `test/services/notification_category_contract_test.dart` now pins the two enums in **both** directions *and* through the real parse path. **5 new pgTAP assertions** (plan 41 → 46: one notice, to the filer, with the sentence, naming the product, carrying the product id for the deep link this phase does not build — and none at all for the two refused closes) and **4 new Dart tests**; analyzer clean, **2,114 pass / 8 skipped**. **Deliberately not built:** tapping the notice goes nowhere new (it marks read and stops), and a **decline** still tells the seller nothing — the row explains why, but only to a seller who opens it. **And the same caveat as both its predecessors: none of it has run**, because both SQL files are written and not applied — CI's `Supabase Migrations` job is the first thing that will apply either, and it will apply them in version order.
**Prev. update:** September 28, 2026 — **V2.11: the queue can now make the model, not only point at one (P2 of the request flow).** V2.10 shipped a door for the sellers who cannot produce a `.glb` — and then left the ask answerable only by someone with a terminal, a handover link and `tool/prepare_shoe_model.dart`, because *Close as done* can only point at a model that already exists. So the admin's card gains **Upload a 3D model**: paste a link, the app fetches the file, runs the authoring contract over it, publishes it through **the same `ShoeModelUploadService` the seller's form uses** (bytes → draft row → `validate-shoe-model` decides), and closes the ask in the same step. Three things are worth reading the code for. *(1) **The seller's own measurement is prefilled, and it is the external one.*** That is the exact opposite of the seller's form, which deliberately refuses to prefill the length because the only number it held was the *internal* last — here the number is the figure the seller measured across the outside of the pair, which is what the renderer scales to (§2.5.2 of the architecture doc), so retyping it would only add a way to mistype it. *(2) A declaration that drifts more than the contract's ±5 mm from that measurement earns a **note, not a gate***: the mesh is scaled to the *declared* figure, so a 20 mm error sizes every shoe wrong — but the admin may know the seller measured the wrong pair, and a warning that blocked a correct model would be the worse rule. *(3) **Publish and close are two writes, and this surface reports both.*** The ending that needed a name is **live but open** — the model is live for customers while the ask is not closed, so the seller still reads "somebody is on it" — and it is amber rather than green or red, with copy that states both halves, because a silent success there would leave a seller waiting forever. **No migration of its own, and that is a design fact rather than luck:** an admin may already insert a `product_models` row and upload to `shoe-models` (both policies read `public.is_admin()`), and `validate-shoe-model` resolves an admin caller the same way — so this is the one phase of the pipeline that needed a screen rather than a schema. The report card was also **extracted** (`lib/widgets/shoe_model_report_card.dart`) so both uploaders read one implementation of "within tolerance", and the seller's form keeps its publish switch by passing it in as the card's footer. One new switch, `AppConstants.adminModelUploadEnabled` (**OFF**), read through `adminModelUploadAllowed` = that flag **and** the pipeline's own `shoeModelUploadEnabled`, so killing the pipeline still kills every writer. **23 new tests** (10 rules, 3 report-copy, 9 sheet, 1 rollback + 2 flag-on in the queue), analyzer clean, **2,110 pass / 8 skipped**. **What it does not do:** the ask still cannot be answered until `20260928140000` is applied — the *close* half is that file's RPC — so the flag-on path has never run against anything but a fake.
**Prev. update:** September 28, 2026 — **V2.10: the pipeline gets a second door, because the first one assumes a seller who does not exist in this market.** The upload path (V2.2/V2.3) presumes a seller who can hand over a contract-compliant `.glb`; CUFMAI's sellers are local artisans, and the evidence is V2.7's own first real asset — a marketplace file that needed a normaliser run before it passed. So the seller can now **ask**: "Request a 3D model" sits in the product action sheet, above Hide/Delete, and the ask lands in an admin queue. The row is **stateful**, because a seller who cannot tell "waiting" from "declined" files duplicates: no request → *Request a 3D model*; open → *3D model requested* plus whose desk it is on; declined → the reason and a retry; a live model → *3D model ready*. **The form asks in the seller's language, not in 3D's:** four fields, one required, measured with a ruler outside the shoe. That is the resolution of the question that started this — *why should a cobbler type a 3D parameter?* — and the one number it will not let them get wrong is the one that matters most: `27` earns a message about **centimetres**, not a range error, because a centimetre figure is plausible to a parser and would scale every mesh four-tenths of life size. The required figure is the **EXTERNAL** length (the renderer's number), deliberately not `products.last_length_mm` (the fit verdict's, 8–15 mm shorter, guide §5) — which is also why the form prefills the heel and the size from the product's fit spec and **refuses to prefill the length**. The database half is `20260928140000_add_shoe_model_requests.sql`: one table, **five `SECURITY DEFINER` RPCs** (file, withdraw, claim, fulfil, decline), **no seller write policies at all** — the rules are multi-row invariants a policy cannot express, so the RPCs are the only door — plus a **partial unique index** that allows exactly one open ask per product, and a `CHECK` that refuses `fulfilled` without a `model_id`. That last one is the point of the feature's honesty: **"done" names a live model of the same product**, enforced in the RPC *and* in the constraint, so an admin cannot close an ask by typing a status. The admin side is a queue under the dashboard's tools (`3D Model Requests`), with tabs that separate work from history, "close as done" as a **picker over the product's own live models** (and a straight answer when there are none), and a **decline that cannot be sent without a reason** — the seller reads that sentence in their own sheet. **59 new tests** (29 pure rules, 15 service, 8 seller row, 7 admin queue), analyzer clean, **2,087 pass / 6 skipped**. The switch is `AppConstants.shoeModelRequestEnabled`, **OFF**, and this time the thing it waits on is an **apply**, not a partner. **⚠️ The one thing to read twice, as it stood on this date: the migration had not been run against any database.** It was written and deliberately not applied (`MIGRATIONS_LIVE_STATUS.md`), and — unlike every other DDL entry in this document's history — it was not measured inside a rolled-back transaction either: the decision was to let CI's `Supabase Migrations` job (`db reset` + `supabase test db` over the 41 new pgTAP assertions) be the first thing that applies it. So the SQL's claims are read, not proven, and the only surface that would exercise them on a device is behind a switch that is off. P2 (the admin's own upload) and P3 (telling the seller it is ready) are not built.
**Prev. update:** September 28, 2026 — **A real partner asset arrived, and the contract's first red rows were fixed rather than filed: V2.7 gains a normaliser.** The file is a marketplace/AI-generated shoe — 31.5 MiB, 49,954 triangles, three 4096² PBR maps, one material called `Material.001` — and it failed **7 of the 11 checks** on exactly the mechanical grounds the guide's §C1–C2 warn about: the scene's Z-up→Y-up rotation was left **on the node** (invisible to a validator that reads accessor bounds, and to the server), the length ran along **X** instead of Z, the shoe stood **4.30× life size** (1160.8 mm long, i.e. 270 mm of shoe), the origin sat at the middle of the shoe, the textures were 4096², and the single material cannot be colour-swapped. All of it is repairable arithmetic, so `lib/utils/glb_normalizer.dart` (**16 tests**) + `tool/prepare_shoe_model.dart` now do it: bake the node transform into the vertices, yaw the length onto +Z (with `--toe` naming the end that is the toe, because a bounding box is symmetric about that question), scale to `--external-length-mm` (never invented — without the declaration it re-axes and re-grounds but deliberately leaves the scale alone, so the scale row keeps failing on purpose), ground/centre to heel-bottom-centre, re-bake textures to ≤1024² (4096² → 1024² JPEG turns 30 MiB of maps into 418 KB), rename and, where the file has only one material, cut a `sole` band geometrically with its area share reported. It **refuses** the two things that cannot be repaired offline — Draco/meshopt geometry (nothing can decompress it here) and KTX2 textures — instead of writing a mangled file. **Result on the real asset: 31.48 MiB → 1.66 MiB, L×W×H 270.0 × 111.7 × 100.7 mm, 11/11 PASS.** Two things the exercise proved that no fixture had: the pipeline's contract is reachable from a *marketplace* file (good news for V2.8/V2.9 sourcing), and the asset is a **shell** — 578 disconnected surface islands, 11,408 open edges — which is the guide's §6 "the model is a lookalike, not the product" row and stays a reviewer decision, not a validator one. Analyzer clean; **2,027 pass / 6 skipped** (20 new); `dart run tool/validate_glb.dart` green on the produced file, and the placeholder asset still passes all 11 after a normalise pass (round-trip test). **And the file is now reachable on a device: the V3.5 QA seam serves it.** `assets/models/qa_partner_shoe_v1.glb` (1.66 MiB) is bundled **for the seam that is off by default**, and `--dart-define=TRY_ON_QA_MODEL=assets/models/qa_partner_shoe_v1.glb` makes the production `ShoeModelService` hand *it* to the renderer instead of the 29,340 B block-out. The reason is specific: the block-out is 1,536 triangles of untextured block geometry, so it cannot tell a renderer that decodes three 1024² PBR maps from one that draws grey clay — which is the failure a mid-range phone is most likely to show. The seam now carries per-asset row numbers (a 49,954-triangle asset reporting the block-out's 1,536 would make the QA comparison meaningless), an unknown `TRY_ON_QA_MODEL` **falls back to the block-out and can be reported as a typo** rather than silently serving the wrong file, and four new tests hold the line — including one that runs the **authoring contract over the bundled bytes**, so the seam cannot carry a file that stopped conforming after the day it was produced

## 0. How to read this roadmap

- **Fit ships before render.** The fastest real value (a trustworthy size verdict on the product page) needs no 3D assets at all, only millimetres the app already has. The 3D try-on follows on top of it.
- **Each phase is independently shippable and independently revertable** (the house rule from `SIZE_AWARE_SHOPPING_PLAN.md`). Visible phases ship behind a const feature flag; P0-style foundations are inert until the flag is on.
- **The long pole is not code — it is 3D assets.** Engineering is ~8–11 weeks; producing 20–50 sellable shoe models is a parallel content programme that starts in week 1, not after the code lands.
- **Effort units:** Small < 3 days · Medium 3–7 days · Large 1.5–3 weeks · Very Large 3+ weeks.
- **Gate before every phase close:** `flutter analyze lib test && flutter test` passes, plus the phase's own exit criteria.

> **V2.2/V2.3 are in code (2026-09-28) — and the phase can now be fed.** Until today the pipeline had a validator, a table, a bucket and a read service, but no way to get a file *in*: every V2 task that mattered ended at a partner holding a `.glb` that nobody could upload. `add_edit_product_screen.dart` now carries a "3D Model (Optional)" section that takes the link and the declaration, fetches the bytes, runs the contract, and publishes on Save. The design points worth reading the code for:
>
> 1. **A link, not a picker — and that is a gap, not a preference.** `image_picker` cannot select a `.glb` and no general file picker is a dependency of this project (verified: `file_picker` is not even transitive), so the handover arrives as a URL the studio shares and `DioShoeModelBytesSource` fetches it — with the byte cap enforced **mid-download** (`CancelToken`), because a wrong link (a Drive preview page) can be arbitrarily large and buffering it whole would be a memory failure on the cheapest phones in this market. The link must be https, except loopback so a developer can stage a file locally. Adding a picker later is a second source feeding the same `ShoeModelAsset`.
> 2. **Bytes before the row, always.** A `product_models` row whose object is missing renders as "no model" at best and as a failed download on every launch at worst, while an object with no row is simply invisible — the same asymmetry V2.5's `.part`-then-rename write protects on the read side, so the upload writes storage first and the table second (and a test asserts that order).
> 3. **Re-publishing a file is a no-op.** The digest is the storage filename, so `shoeModelReuseMatch` finds the existing row and flips its status instead of writing a duplicate — without that rule, "publish this model again" would create a second row pointing at one object and give the resolver two candidates for one asset.
> 4. **A failed check is a report, not an exception.** The seller has to read *which* rows failed, so the check returns a report either way; only a transport problem (bad scheme, 404, private link, unreachable host) throws, and each cause has its own sentence.
> 5. **A model failure never rolls back the product.** The upload runs after the product row is saved and reports itself in the snackbar ("Product saved, but the 3D model did not upload…") — losing the seller's product to a bad asset would be the D8 mistake in reverse.
>
> **Three deferrals, each because a required input does not exist yet.** *(a) The file picker* — no dependency can select a `.glb`, so the link is what ships. *(b) The per-colour override* (`variant_id`) — the app's variants are colour **and** size (`{'color': 'Black', 'size': 'EU 42'}`), so attaching a model to one variant id would show it on exactly one size: the resolver's exact-match rule would faithfully honour a row that means something the seller never intended. A per-colour model needs either a colour column or a resolution rule by colour, and that is its own decision (D-2). *(c) The material map* — `product_models.material_map` stores `{part: {baseColorHex, metallic, roughness}}`, but the product's colours are free-text **names** with no paint value (`product_color_images` carries only a photo URL), and the repo's single name→colour map (`lib/utils/variant_swatch_color.dart`) is a **UI swatch** whose unknown-name branch is a deterministic *synthetic* fallback. Adopting it as albedo would paint a shoe a colour nobody chose — the same mistake the fit card refuses to make by hiding a verdict it cannot support. The column, `ShoeModelSpec.materialMap` and the validator's approved-part check all stay ready for a real paint value.
>
> **Why the section was off, and why it now ships on (2026-09-28).** `shoeModelUploadEnabled` used to default to `false`, with `--dart-define=SHOE_MODEL_UPLOAD=true` to opt in, on the reasoning that V2.1's table and bucket were unwritten: a shipped build's Upload button could then only ever produce "relation does not exist", and a broken button is worse than an absent section. **That reasoning was sound and its premise was false** — the table had already been applied and never recorded, so the switch was waiting on nothing. It now defaults to `true`; `--dart-define=SHOE_MODEL_UPLOAD=false` restores exactly the previous day's form, and the kill switch is read by the save path as well as the section, so turning it off cannot leave a half-published model. **The caveat that outlives the flip:** the pipeline is now *reachable*, not *fed* — `product_models` holds 0 rows until a partner hands over a real `.glb`, so the section is live for every seller and there is nothing to show it yet.

**Exit criteria:** 3 **real pairs** have been captured with their partners, cleaned, and have validated active models that download and cache on device — declaration sheet and validator output attached to each; a deliberately broken GLB is rejected both client- and server-side; cache eviction proven under the 50 MB budget.
**Rollback:** assets are additive; disable by leaving `status='draft'`.

> **Four things this entry pinned, each because the alternative was a bug on a device.** *(1) What a phase means:* a phase describes the **AR session**, a mode describes the **surface** — so a product with no model is `idle` with a stated reason, not an error, and V5's error dashboards will not fill up with "this pair has no 3D model". *(2) The flag gates side effects (F19):* with `tryOnV3Enabled` off, the controller reads nothing, downloads nothing and makes **zero channel calls**, which is tested rather than asserted in prose. *(3) The handover precedes the view (F18):* the model is handed to native the moment it is verified, because the plugin parks it — the V0 plugin applied it through `currentView?.` and silently dropped it, which is the bug this ordering exists to not repeat. *(4) The start refuses without a view (F17):* `startAr({required bool arViewReady})` will not call `startSession` unless its caller says the platform view is mounted, so the documented 15-second deadlock becomes an inert fallback with `TryOnDegradeReason.arViewNotReady`.
