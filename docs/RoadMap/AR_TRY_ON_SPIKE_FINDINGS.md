**Bottom line:** the *route* is proven to compile, package and boot (§4); the *numbers* V0

glTF model at all (F14). Treat V0 as "code done, measurement pending", not "spike passed".

## 3. Findings

### F1 — SceneView 4.34.0 is the newest release that works on this toolchain, and it is a hard ceiling

Published versions (Maven Central `maven-metadata.xml`, read 2026-09-27) run
`… 4.34.0 → 4.35.0 → 4.37.0 → 4.38.0 … 4.42.0`; there is no `4.36.x` and no
`4.35.1/4.35.2`. Reading each AAR's own metadata:

| SceneView | `minCompileSdk` in its AAR metadata | Compose BOM it pins |
| --- | --- | --- |
| **4.34.0** | **1** ✅ | 2026.06.01 → Compose 1.11.4 (minCompileSdk 35) |
| 4.35.0 | 37 ❌ | 2026.06.01 |
| 4.37.0 | 37 ❌ | 2026.06.01 |
| 4.42.0 (latest) | 37 ❌ | 2026.09.00 → Compose 1.12.x (compileSdk 37) |

The app is on compileSdk 36 / AGP 8.11.1, so **4.34.0 is the ceiling, and there is no
incremental step above it**: the very next release already requires compileSdk 37.
Compose 1.12.x additionally needs AGP 9.1.

**Consequence:** bumping SceneView later is an **app-wide toolchain upgrade**
(AGP 9.x + compileSdk 37 + Compose alignment), not a dependency edit. Plan it as such
(see §7 D1). Evidence command:

```bash
curl -sS https://repo1.maven.org/maven2/io/github/sceneview/arsceneview/4.35.0/arsceneview-4.35.0.aar \
  | python -c "import sys,io,zipfile;z=zipfile.ZipFile(io.BytesIO(sys.stdin.buffer.read()));print(z.read('META-INF/com/android/build/gradle/aar-metadata.properties').decode())"
```

### F2 — 4.34.0 does not smuggle in an ARCore upgrade

`arsceneview-4.34.0.pom` declares `com.google.ar:core:1.54.0` — exactly the version the
shipped foot scan is built against (`android/app/build.gradle`). Also: `kotlin-stdlib`
2.4.10, `core-ktx` 1.18.0, `appcompat` 1.8.0. Nothing else in the AR stack moved.

### F3 — Kotlin 2.2.20 → 2.4.20 (and the Compose compiler plugin) is now part of the app's build

`android/settings.gradle` pins `org.jetbrains.kotlin.android` and
`org.jetbrains.kotlin.plugin.compose` at **2.4.20**; `android/app/build.gradle` adds
`buildFeatures { compose true }` and applies the Compose plugin. The bump was made for
the 4.42.0 attempt (its metadata is not readable by the 2.2.x compiler) and kept after
pinning 4.34.0, because 4.34.0 still declares `kotlin-stdlib 2.4.10`.

**Build-pipeline note:** a release build now prints `Info: Class … has malformed
kotlin.Metadata: … version 2.4.0, while maximum supported version is 2.2.0` — informational,
not fatal (the build succeeds). It names SceneView classes *and* unrelated plugins
(`mobile_scanner`, `local_auth`, `video_player`), i.e. it is the Kotlin bump speaking, not
SceneView. Something in the release pipeline ships a Kotlin-metadata reader older than our
compiler.

**Caveat recorded on purpose:** we did **not** re-test 2.2.20 against 4.34.0. Reverting
the Kotlin bump is a fresh compile experiment, not a no-op — do not "clean it up"
without running the Gradle build.

### F4 — Compose is a hard requirement of SceneView 4.x, and this app had no Compose before

SceneView 4.x deleted the View-based `ARSceneView`; it is a Compose SDK. The spike hosts
`ComposeView` inside a `PlatformView` — the same shape SceneView's own Flutter bridge
uses, so the spike exercises the integration route rather than a detour around it.
Dependencies added: `androidx.compose:compose-bom:2026.06.01` + `ui` + `runtime` +
**`foundation`**.

`foundation` is listed explicitly because SceneView declares it at **runtime** scope,
while the spike calls `Modifier.fillMaxSize()` — that needs foundation on the **compile**
classpath. Removing that line breaks the Kotlin build.

**Operational finding (measured while building the A/B of §5.3):** Compose is all-or-nothing
per module. Removing only the dependencies fails compilation with
`IncompatibleComposeRuntimeVersionException: The Compose Compiler requires the Compose
Runtime to be on the class path, but none could be found` — the Compose compiler plugin runs
whenever `buildFeatures { compose true }` is set, regardless of whether any source file uses
it. Stripping Compose means removing the plugin, `buildFeatures.compose`, and the
dependencies **together**, in the whole module.

Cost of this decision: F11.

### F5 — The SceneView README's ARCore snippets are SceneView *extensions*, not SDK methods

README-style code such as `frame.getUpdatedPlanes()` and `trackable.createAnchorOrNull(pose)`
compiles only because SceneView ships those as Kotlin extension functions, verified by
`javap` against the artifacts we resolved:

* `io.github.sceneview.ar.arcore.FrameKt.getUpdatedPlanes(Frame)` ✅ (SceneView)
* `io.github.sceneview.ar.arcore.TrackableKt.createAnchorOrNull(...)` ✅ (SceneView)
* `io.github.sceneview.ar.arcore.HitResultKt.createAnchorOrNull(...)` ✅ (SceneView)

On **ARCore 1.54 itself**, `javap com.google.ar.core.Frame` / `Session` shows:

| Wanted | Exists on ARCore 1.54? | Plain-API equivalent used by the spike |
| --- | --- | --- |
| `Frame.getUpdatedPlanes()` | ❌ not an SDK method (extension only) | `session.getAllTrackables(Plane::class.java)` (also valid: `frame.getUpdatedTrackables(Plane::class.java)`) |
| `Frame.createAnchorOrNull(pose)` | ❌ not an SDK method (extension only) | `session.createAnchor(pose)` |
| `Frame.getUpdatedTrackables()` (no-arg) | ❌ (extension only) | `frame.getUpdatedTrackables(Plane::class.java)` |
| `Frame.getUpdatedTrackables(Class)` | ✅ | — |
| `Frame.getUpdatedAnchors()` | ✅ | — |
| `Frame.hitTest(float, float)` | ✅ | — |
| `frame.camera.trackingState` | ✅ | — |

**Consequence for the architecture doc and for V3/V4:** code samples must not be copied
from SceneView's README. Either use the ARCore calls above, or import the extension
explicitly (`import io.github.sceneview.ar.arcore.getUpdatedPlanes`) — and note the
extensions are invisible to a Java-only codebase.

### F6 — The manifest needs `tools:replace` on the ARCore meta-data

SceneView's manifest declares `<meta-data android:name="com.google.ar.core" android:value="optional"/>`;
the app declares the same key as `required`. Without the override, the manifest merger
fails. `AndroidManifest.xml` now carries `xmlns:tools` plus
`tools:replace="android:value"` on that element, keeping the app's `required` value — the
foot scan depends on it. Remove neither the attribute nor the comment explaining it.

### F7 — A JVM signature clash that costs a comment

A Kotlin property named `modelScale` in `ArTryOnSpikeView` generated
`private setModelScale(F)V`, colliding with the channel-facing `fun setModelScale(scale: Float)`
at the JVM level. The backing state is therefore named `modelScaleFactor`. Anyone
"tidying" that name will break the build; the comment in the file explains it.

### F8 — Lifecycle and teardown ownership

`ARSceneView` follows the **host activity's** `Lifecycle`, so pausing the app pauses the
session and the camera. The spike passes the activity lifecycle in explicitly rather than
letting SceneView discover a `ViewTreeLifecycleOwner` through Flutter's view tree — the
Flutter tree has no such owner. Teardown is owned by `PlatformView.dispose()` (the
composition leaving), matching the rule the shipped foot scan already follows. Session
start is driven by composition, not by the `startSession` call, which is why the plugin
parks the `MethodChannel.Result` and answers it on resume / failure / 15 s timeout —
the same reply-leak safety net as `ArFootSizingPlugin`.

### F9 — How model files load, and why the spike sends `file://`

`rememberModelInstance(modelLoader, path)` → `FileLoader.readFileBuffer`, which resolves
**plain paths from APK assets**, **`file://` from the filesystem** (`File(uri.path)`),
and **`https://` via `FileCache` + Fuel**. The spike stages the bundled asset to
`getApplicationSupportDirectory()/spike/placeholder_shoe_$n.glb` and hands over a
`file://` URI, so the code path exercised is the one a downloaded model will take — not
the asset path, which will not exist in production.

Also measured on the fixture (read back from the GLB's JSON chunk):

| Property | Value |
| --- | --- |
| File size | 29,340 B (declared GLB length matches; no trailing bytes) |
| Meshes / primitives | 1 mesh, 2 primitives — materials `sole` and `upper` |
| Geometry | 386 vertices + 768 triangles per primitive → **772 vertices / 1,536 triangles** |
| Attributes | `POSITION`, `NORMAL` only (no UVs, no textures, no images) |
| Bounding box | 94.26 × 94.17 × **270.0 mm** (X × Y × Z) |
| Origin / orientation | heel-bottom-centre at origin, toe along **+Z**, Y-up, metres |
| Compression | **none** — no `extensionsUsed`, uncompressed single-file GLB |
| Buffer | 27,744 B, embedded in the GLB |

This is 0.6 % of the architecture §2.11 GLB budget (≤5 MB), so the fixture cannot tell us
anything about load time for a realistic asset — only that the pipeline works.

### F10 — The fps probe is a UI-level proxy, and that is on purpose

`PerfProbe` samples `Choreographer` over 5 s windows and emits nothing for a window with
no frames (so a paused session cannot report a fake 0 fps). It measures **frames presented
while the AR surface is on screen**, which includes Flutter's own frame work — not
Filament's internal render loop. That is the right number for "what does the user
experience", and the limitation should be stated in any V0 report. If ground truth on the
renderer itself is needed later, use Filament frame callbacks or `dumpsys gfxinfo`.

### F11 — Cost measurements (see §5 for the tables)

Measured, in increasing order of usefulness: native libraries per ABI (§5.1), class payloads
of the added libraries (§5.2), and — since 2026-09-27 — the **release A/B delta the §2.11
budget is written against** (§5.3): **+27,716,757 B all-ABI, ≈+15.7 MB per device. The budget
fails.** The dominant cost is the Compose dex plus SceneView's packaged Filament assets, not
the native renderer.

### F12 — Two ARCore sessions in one process is an *unverified* risk

`ArFootSizingPlugin` and `ArTryOnSpikePlugin` both exist in the process today, each
capable of creating its own ARCore session (the view-based GL renderer and
`ARSceneView` respectively). They are never run at the same time, and the spike proves
only that **registering** two plugins is fine. ARCore allows a single active session per
process. Before V3, verify that navigating scan → try-on (or back) releases the first
session cleanly; a leaked session shows up as a camera-open failure, not a crash.

### F13 — The renderer's JNI libraries are never loaded for us (found on the emulator, fixed)

`filament-jni` and `gltfio-jni` are loaded from the static initialisers of two classes — and
**nothing in SceneView or ARSceneView touches them**. Verified by disassembly of all four AARs
(`filament-android`, `gltfio-android`, `sceneview`, `arsceneview`): `com.google.android.filament.Filament`
and `com.google.android.filament.gltfio.Gltfio` are the only `loadLibrary` sites in the whole set,
and no other class references them.

Not a theory — the first emulator run died on it:

```
E .solevision.app: No implementation found for long com.google.android.filament.Engine.nCreateBuilder()
                   (tried Java_com_google_android_filament_Engine_nCreateBuilder …) - is the library loaded?
java.lang.UnsatisfiedLinkError … at com.google.android.filament.Engine.create(Engine.java:584)
```

**Consequences.** The spike would have crashed on the customer's first tap at V0.6 — the kind of
defect that burns a device session. `ArTryOnSpikeView` now calls `Filament.init()` +
`Gltfio.init()` in its `init` block (both idempotent, ~no cost until the spike screen opens),
and `GltfioDecodeTest` documents the same trap. The V3 production view must do the same.

### F14 — At feature level 1 **no glTF model loads at all**, and the emulator cannot answer V0.7

Measured on the Pixel_4 emulator (API 37): the engine comes up on OpenGL with
`supportedFeatureLevel = FEATURE_LEVEL_1` (i.e. OpenGL ES 3.0), and every asset load then fails with

```
E Filament: No material with the specified requirements exists.
```

for **all three fixtures — including the uncompressed control** — with retries and
`Engine.flushAndWait()` in front of each attempt. The ubershader material provider is what fails:
a plainly-keyed request resolves, the fixtures' primitives do not. SceneView ships **precompiled**
`*.filamat` materials for its own rendering and *those load fine at level 1* (measured), which is why
`GltfioDecodeTest` proves the material path separately.

**Two consequences, one of them commercial:**

1. **Emulators cannot validate model loading.** V0.6's "needs a physical device" was an assumption
   until now; it is now a measured fact with a mechanism. The decode test skips itself on such a
   target and says why.
2. **Low-end devices are a compatibility risk for the whole feature.** Any phone limited to OpenGL
   ES 3.0 — exactly the class of device a Carcar City customer is most likely to hold — apparently
   cannot render a 3D shoe through the ubershader path. This is unverified on real hardware and must
   be checked on the low-end device of the V0.6 matrix before any partner is told the feature exists.
   If it reproduces, the mitigation is a material provider built on precompiled materials (the
   pattern SceneView already uses for its own), at the cost of the ubershader's automatic variants.

### F15 — The first asset load after `Engine.create()` is not deterministic

Observed on the emulator: the same uncompressed fixture loaded, then failed, then failed
consistently. The engine's driver comes up on its own thread (`FEngine resolved backend: OpenGL` is
logged from a different thread id than `Engine.create()`), and an asset created too early fails
material resolution. `Engine.flushAndWait()` plus a bounded retry is what `GltfioDecodeTest` uses to
make results repeatable. Whether this matters on a real device is untested — but it is the same
class of trap as F13, so the production loader should flush-and-retry rather than assume the first
attempt is meaningful.

### F16 — A material/mesh mismatch **aborts the process**, it does not fail the load

Handing gltfio a material whose requirements the mesh cannot satisfy — a material without the
parameters gltfio sets (`baseColorFactor`, `metallicFactor`, …) or with attributes the mesh lacks —
trips `utils::PreconditionPanic` inside `AssetLoader::createAsset`:

```
F libc++abi: terminating due to uncaught exception of type utils::PreconditionPanic: Precondition
F libc: Fatal signal 6 (SIGABRT) … (filament::gltfio::AssetLoader::createAsset)
```

Reproduced twice (with `camera_stream_depth.filamat`, then `opaque_colored.filamat` as the stand-in
provider). **The authoring checklist is therefore a crash-risk list, not a style guide:** a captured
model whose materials reference textures or tangents the mesh does not carry can abort the app
rather than render oddly. It is the strongest argument yet for the V2.7 validator and for loading the
first real asset on a device before any partner sees it.

### F17 — The view/session handover order is load-bearing, and **both ends of it were wrong**

Found by reading the spike's own request sequence, not by a device run — which matters, because
these two defects would have consumed the entire V0.6 device session and produced a false verdict
("ARCore never starts on this device").

| End | Defect | Why it was fatal |
| --- | --- | --- |
| Dart | The AR view was only rendered once `_preparing` flipped false, and that happened **after `await startSession()`** — but the native session cannot resume until the view exists, and the session resuming is what answers `startSession` | Self-deadlock: spinner for the full 15 s safety net, then a `timeout` verdict, on every device, every launch |
| Native | `setModel` / `setModelScale` arrived **before** the platform view existed, and the plugin applied them through `currentView?.` | Silently dropped — a no-op. Even after the deadlock was fixed the scene would have stayed empty, now reported as "model never loads" |

Fix, both halves: Dart renders the view **before** awaiting the session and hands the model over
first; the plugin **parks** the model path and scale and applies them when the view factory creates
the view (the same park-then-answer pattern the shipped plugin already uses for `startSession`).
Pinned by widget tests that hold the native `startSession` reply **open** on purpose and assert that
the view is already on screen with `setModel`/`setModelScale` already dispatched — the only way to
assert deadlock-freedom without hardware.

```bash
# the regression tests (the flag-dependent ones skip themselves without the define)
flutter test --dart-define=AR_TRY_ON_SPIKE=true test/screens/ar_try_on_spike_screen_test.dart
flutter test test/screens/ar_try_on_spike_screen_test.dart   # flag-off: must be inert
```

### F18 — Defence in depth has to cover side effects, not just the UI

The dev flag was checked **only in `build()`**, so a build without `--dart-define=AR_TRY_ON_SPIKE=true`
still asked for camera permission and still staged the model into app storage on mount — the screen
was inert to look at and active underneath. The guard now sits in `initState` too: a disabled build
requests no permission, opens no channel and writes no file. Caught by the flag-off widget test
(which asserts no channel calls and no staging directory), and the reason it is worth a test is that
this is exactly the class of leak that ships: invisible in the UI, visible to the user as a
permission prompt they never asked for.

### F19 — The staged-file cleanup deleted the file it had just written

The reload path deleted "everything in the staging directory except the file I just wrote" by
comparing raw path strings. `Directory.listSync()` and a hand-built `'$dir/$name'` need not spell the
same separator — on the Windows test host the listing spelled `\` while the new file spelled `/`, so
the just-staged model matched "not mine" and deleted itself; the reload handed native a path that no
longer existed. On Android both sides spell `/`, so this would have been invisible on the device and
then bitten during V2 when real models land in that directory. Fixed by clearing the directory
**before** the write: same delete-all intent, impossible to delete the model being handed over, and
it also removes the race between two staging passes (double-tapping Reload).

### F20 — The Filament-direct route ships **no assets**, so the camera feed, the plane visual and IBL are ours to supply

Measured 2026-09-28 by unzipping the three artifacts the production route depends on:
`filament-android`, `gltfio-android` and `filament-utils-android` 1.72.1 each contain **zero** files
under `assets/`. Every `.filamat` and `.ktx` in a SceneView build belongs to SceneView — which is
exactly why removing it is worth 3,305,732 stored bytes (§5.5).

That has a consequence the size measurement alone does not show: the three things SceneView
supplied are not "a helper class", they are **files**, and a Filament renderer cannot draw the
camera feed or a plane without a material:

| What it needs | The file SceneView carried | Size |
|---|---|---|
| Camera feed as a background | `assets/materials/camera_stream_flat.filamat` | 42,544 B |
| Floor plane visualization | `assets/materials/plane_renderer.filamat` | 40,976 B |
| Image-based lighting (reflections) | `assets/environments/neutral_ibl.ktx` (+ skybox) | 2,095,464 B (+1,572,932 B) |

**Hand-building the geometry instead is not the way out.** F16 is a measured SIGABRT: a
material/mesh mismatch trips `utils::PreconditionPanic` inside `AssetLoader::createAsset`, so a
full-screen quad or a plane mesh built against an ubershader whose exact attribute and parameter
set has not been verified *is* that crash, on a customer's screen.

Two honest routes, both open. **Vendor the two small `.filamat` files** (~85 KB total, Apache-2.0)
into `android/app/src/main/assets/materials/` — after checking they load on Filament 1.72.1, because
a `.filamat` is version-locked to the `matc` that compiled it, so this is a test and not a copy. Or
**compile our own with `matc` in CI**, which is more work and removes the licensing question. The
IBL is optional and much larger: without it the shoe has no reflections and reads slightly flat —
a look problem, not a correctness one, which is why the built view ships two directional lights and
no environment map.

### F21 — A marketplace/AI-generated `.glb` is the realistic partner asset, and its failures are arithmetic, not modelling

Measured 2026-09-28 on the first real file to arrive (`docs/RoadMap/SHOE_MODEL_AUTHORING_GUIDE.md`
§C9, roadmap V2.7). It is a brown leather shoe — the base colour map shows stitching, a quilted
panel and printed size labels, and a textured render reads unmistakably as footwear — but nothing
about it came out of a capture pipeline.

| Property | Measured |
|---|---|\n| File | 31.48 MiB `.glb`, `Khronos glTF Blender I/O v4.0.43` |
| Geometry | 49,954 triangles, 31,120 vertices, non-interleaved float attributes |
| Textures | three 4096² PNGs: base colour (12.60 MiB), normal (7.55 MiB), metallic+roughness (10.08 MiB) |
| Materials | **one**, `Material.001`, `doubleSided`, `KHR_materials_specular` (factor 2.0) |
| Bounding box | 1160.8 × 480.3 × 433.1 mm — a **270 mm shoe at 4.30× life size**, lying with its length on X |
| Topology | **578 disconnected surface islands, 11,408 open (one-sided) edges** — a shell, not a solid; 2.9% of shared edges are creases, so it is smooth-ish, not faceted |
| Surface | 1.84 m², of which 17.8% faces within 8° of up and 11.5% of down — the sole plate plus the upper |
| Nodes | one root node carrying `+(90°) about X`, i.e. the exporter's Z-up→Y-up conversion **left unapplied** |

**The finding is what the 11 checks said, and why.** Seven failed: `file size`, `materials`,
`textures`, `units`, `orientation`, `origin`, `scale`. None is a modelling defect. The most
instructive one is `orientation`: because `glb_validator.dart` — and the server-side mirror, and
any headless reader of accessor bounds — judges the mesh **in its own local frame**, while a
renderer obeys the **node tree**, this file was simultaneously *failing the contract* and
*rendering the right way up*. Two readers of one file disagreed about which way is up, and no
amount of staring at the export dialog would have shown it.

**Consequence, and what was built for it:** `tool/prepare_shoe_model.dart` +
`lib/utils/glb_normalizer.dart` (roadmap V2.7) do the arithmetic — bake the node transform into the
vertices *and* normals, yaw the length onto +Z with `--toe` naming the toe end, scale to the
declared external length, ground and centre at the heel-bottom, re-bake textures to 1024², rename
parts or cut a `sole` band from a single-material mesh. Result: **31.48 MiB → 1.66 MiB, 270.0 ×
111.7 × 100.7 mm, 11/11 PASS.** Two refusals stay refusals: Draco/meshopt geometry (nothing here can
decompress it) and KTX2 textures (nothing here can decode them), each answered with the re-export
instruction rather than a file with an unverifiable claim in it.

**What no tool fixes, and the part that matters for V2.8/V2.9 sourcing:** a shell with 578 islands
whose normals and interior are reconstruction artefacts still *is* a lookalike, not the partner's
product — the guide's §6 row and checklist items 6/7. The normaliser can make a bought asset
**load**; only a partner can make it **the shoe**. That is why V2.8 (three captured products) stays
the critical path, and why a marketplace file is a useful rehearsal for the pipeline and a poor
substitute for the sample.

### 5.6 The production view exists, and what it cost to write (§5.4 item 3 is the bill)

2026-09-28, same day as the measurement above: the route stopped being a number and became code.
`android/app/src/main/kotlin/com/solevision/app/tryon/ArTryOnView.kt` drives Filament 1.72.1
**directly** — `Filament.init()`, `Gltfio.init()`, one render thread owning engine, renderer,
swapchain, scene, view and camera, and ARCore's own `Pose.toMatrix` + `getProjectionMatrix` as the
camera's model matrix and custom projection, so the shoe is world-anchored correctly *before* the
camera feed exists. `ArTryOnPlugin.kt` beside it carries the method/event surface Dart already
speaks, parks a `setModel` that arrives before the view (F18) and answers a `startSession` with no
view as `timeout` after 15 s rather than hanging (F17).

Three API facts cost the first compile, and they are worth recording because they are invisible in
documentation searches:

1. **ARCore 1.54's convenience getters are gone.** `Camera.getProjectionMatrix()` and
   `Pose.toMatrix()` exist only as out-param forms (`(dest, offset, …)`), and
   `LightEstimate.getColorCorrection(dest, offset)` likewise — there is no float[]-returning
   overload to call. Confirmed with `javap` against the AAR, not guessed.
2. **Filament's Java API differs from its C++ documentation.** `View.setViewport` takes a
   `Viewport` object, `Renderer.ClearOptions.clearColor` is a `double[]`, `LightManager.Builder` is
   a nested class (not a member of the manager instance), and `FilamentAsset` exposes **no**
   material-instance list — instances are reached per renderable, per primitive, through
   `RenderableManager`.
3. **The camera feed is not the only missing asset** — see F20 above. Model rendering needed none
   of them, which is why this landed without the `.filamat` question being settled.

**What the build therefore does and does not do.** Does: the ARCore session lifecycle with the
chapter-2 error taxonomy, a key/fill light pair with the key driven by ARCore's ambient light
estimate, model load with the destroy-then-create swap and the measured flush-and-retry, uniform
scale from `authored_length_mm` and the §2.6 grading step, colour overrides, ARCore hit-test floor
placement with an analytic floor ray as the pre-detection fallback, a perf probe, a PixelCopy
screenshot, and full teardown on the render thread. Does **not**: composite the camera feed, draw a
plane, or use an environment map (F20), and **nothing here has run on a device** — it compiles, and
that is the whole claim. fps, load ms, tracking quality and whether the ubershader resolves on real
hardware are all still V0.6's to answer.

One consequence for the spike: `GltfioDecodeTest.engine_capability_report` asserts that
`assets/materials/*.filamat` exist in the app APK, which is true only while SceneView is a
dependency. Retiring the spike and deleting `arsceneview` means editing that assertion — it tests
**SceneView's** materials, not ours.

**What this means for "is V0 finished?":** the *code half* is finished and verified as far as this
machine can verify anything — it builds, packages, boots on Android, registers its channels, sizes
itself, and its Dart contract has tests. The *evidence half* is gated on exactly two things that are
not code: **a physical ARCore phone** (V0.6, V0.7's compression half) and **a partner's sample shoe**
(V0.4–V0.5). No amount of further engineering here substitutes for either.

### What the spike deliberately still does not do

No tap-to-place, no occlusion (architecture §2.10), no foot tracking, no size-chart-driven scale
(the slider is the seam), no colour/variant selection, no model caching or eviction, no https model
load, no iOS, and no multi-model scene. All of it is V3+ work and none of it is blocked by V0.
