# Product Architecture — SoleVision (CUFMAI)

> Current-state reference for the product system, with a deep dive on the
> **Adjust Stock** feature. Written after the stock-persistence hardening
> pass (Aug 2026). Supersedes the older `PRODUCT_ARCHITECTURE_CONTEXT.md`
> for anything stock-related — this doc reflects the **fixed** flow.

---

## 1. Quick Facts

- **Stack:** Flutter + Supabase (Postgres, Storage, Realtime)
- **State management:** ChangeNotifier + Provider (`ProductProvider` at app root)
- **Product ID type:** `TEXT` (UUID stored as text)
- **Stock is stored in TWO tables that must never drift:**
  - `inventory` — **AUTHORITATIVE** for checkout, customer browse, and Adjust Stock
  - `product_variants` — per size+color rows, **AUTHORITATIVE** for the seller add/edit form
- **Storage bucket:** `product-images` (public read)

---

## 2. Data Model (Stock-Relevant Tables)

### products

```sql
CREATE TABLE public.products (
  id              TEXT PRIMARY KEY DEFAULT gen_random_uuid()::text,
  store_id        UUID REFERENCES public.stores(id),
  seller_id       UUID REFERENCES public.profiles(id),  -- nullable! (see §8 Gotchas)
  name            TEXT NOT NULL,
  description     TEXT,
  price           NUMERIC NOT NULL CHECK (price >= 0),  -- always the ORIGINAL price
  category        TEXT NOT NULL DEFAULT 'General',
  tags            TEXT[] DEFAULT '{}',
  collection      TEXT,
  sku             TEXT,
  is_active       BOOLEAN NOT NULL DEFAULT true,        -- auto-synced to stock levels
  is_featured     BOOLEAN NOT NULL DEFAULT false,
  is_published    BOOLEAN NOT NULL DEFAULT true,
  sale_price      NUMERIC,                              -- discounted price while on sale
  sale_starts_at  TIMESTAMPTZ,
  sale_ends_at    TIMESTAMPTZ,
  created_at      TIMESTAMPTZ DEFAULT now(),
  updated_at      TIMESTAMPTZ DEFAULT now()
);
```

**RLS:** anyone can `SELECT`; only `role IN ('seller','admin')` can INSERT/UPDATE/DELETE (migration `20260712_tighten_products_rls.sql` verifies `store_id` ownership on top).

### product_variants  (size × color combos)

```sql
CREATE TABLE public.product_variants (
  id               BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  product_id       TEXT REFERENCES public.products(id) ON DELETE CASCADE,
  size             TEXT NOT NULL,
  color            TEXT,
  stock            INTEGER NOT NULL DEFAULT 0 CHECK (stock >= 0),
  additional_price NUMERIC NOT NULL DEFAULT 0 CHECK (additional_price >= 0),
  sku              TEXT
);
```

**RLS:** anyone can `SELECT`; writes require `products.seller_id = auth.uid()` or admin.

### inventory  (aggregated stock by size)

```sql
CREATE TABLE public.inventory (
  product_id  TEXT REFERENCES public.products(id) ON DELETE CASCADE,
  size        TEXT NOT NULL,
  stock       INTEGER NOT NULL DEFAULT 0 CHECK (stock >= 0),
  updated_at  TIMESTAMPTZ DEFAULT now()
  -- ⚠️ LIVE DB: UNIQUE (product_id, size) named "inventory_product_id_size_key"
  --    schema.sql documents PRIMARY KEY (product_id, size) — docs ≠ live DB.
);
```

**RLS:** anyone can `SELECT`; writes require `products.seller_id = auth.uid()` or admin.

One row per unique size; stock is the sum across all colors of that size.

### Relationship graph

```
products (1) ──→ (N) product_variants   (per size+color, per-color stock)
products (1) ──→ (N) inventory          (per size, aggregated stock — AUTHORITATIVE)
products (1) ──→ (N) product_images
products (1) ──→ (N) product_customizations
products (1) ──→ (N) order_items / sales_transaction_items / cart_items
```

## 3. The Two Stock Sources & the Sync Invariant

The single most important rule of this system:

> **`inventory` and `product_variants` must always agree on per-size totals.**

They can temporarily disagree mid-write, but every completed operation leaves
them in sync. Two write paths keep them in sync, in opposite directions:

| Writer | Writes first | Then syncs | Direction |
|--------|-------------|-----------|-----------|
| **Seller Add/Edit form** (`ProductService`) | `product_variants` (delete + re-insert) | `_syncInventoryFromVariants()` — deletes & regenerates `inventory` FROM variants | variants → inventory |
| **Adjust Stock** (`SupabaseService`) | `inventory` (upsert) | `_syncVariantStock()` — distributes inventory totals ONTO variant rows | inventory → variants |

**Why this matters:** if Adjust Stock wrote only `inventory`, the next product
edit would regenerate `inventory` from stale variants and **silently wipe every
stock adjustment**. The dual sync is what closes that loop.

## 4. Read Paths (who reads stock, and from where)

| Surface | Query | Stock source |
|---------|-------|--------------|
| Customer browse (Home, Store, Collection) | `SupabaseService.fetchProducts(hideOutOfStock: true)` | `inventory` (joined) |
| Customer product detail / cart | `fetchProducts` joins both | `inventory` (higher-wins merge with variants) |
| **Checkout** | `order_service`/`cart_service` resolve via `resolveInventoryStock()` | `inventory` — missing match ⇒ out of stock |
| POS / seller screens | `ProductProvider.loadSellerProducts()` → `fetchProducts(storeId:)` | `inventory` + `product_variants` |
| Manage Products grid | `ProductService.getSellerProducts()` (raw rows, all relations) | `inventory` first, variants fallback |
| Edit product form | `ProductService.getProduct()` | `product_variants` (form edits variants) |

### Restock lifecycle (hide → reappear)

```
Seller restocks via Adjust Stock
  └─ inventory row goes from 0 → N
      └─ next customer fetch: fetchProducts(hideOutOfStock: true)
          └─ purchasableProducts() (lib/utils/product_stock.dart)
              └─ product.totalStock() > 0  →  product REAPPEARS in catalog
```

An out-of-stock product (zero stock on every size) is dropped from customer
browse **exactly when it is unpurchasable**, because `purchasableProducts`
uses the same `inventory` source that checkout validates against. Legacy
products with no inventory rows at all total 0 and are also hidden.

`totalStock()` / `isOutOfStock()` / `purchasableProducts()` live in
`lib/utils/product_stock.dart` as pure functions (unit-tested — §7).

## 5. Adjust Stock — Deep Dive

### 5.1 Entry point & UI

**Where:** `lib/screens/seller/manage_products_screen.dart`
**How:** long-press a product card → **Adjust Stock** (the standalone inventory
screen was merged here). Also reachable conceptually from the Low-Stock /
Out-of-Stock filter chips (deep link via `initialFilter`).

`_showStockEditor(product)`:

1. **Builds the editable `sizes` map** (`{size: stock}`):
   - From `product['inventory']` (authoritative) when rows exist.
   - **Variant fallback:** if no inventory rows (legacy product), sums
     `product_variants` per size so the editor always has sizes to edit.
2. **`maxStock` per row** = `totalMax + 10` (or 20 when empty) — the `+` button
   clamps at this cap.
3. **`liveSizes`** — a *mutable* map captured once at sheet open. Every change
   mutates it and persists the **whole map**, so adjusting size A then size B
   can never revert A (the old snapshot-at-open bug).
4. **`writeChain`** — a `Future` chain that **serializes DB writes**. Rapid
   taps enqueue writes; each queued write persists the full map, so the last
   write always reflects the final state. No out-of-order landing.
5. Renders one `SellerInventoryRow` per size inside a modal bottom sheet.

### 5.2 SellerInventoryRow (the +/- stepper)

**File:** `lib/widgets/seller/seller_inventory_row.dart`

- Each tap: `_stock` clamped to `[0, maxStock]` (uses `widget.maxStock`, NOT a
  hardcoded cap), shows a saving spinner.
- **800ms debounce:** after the last tap, `widget.onStockChanged(_stock)` fires.
- **Fires even if the row was disposed** (e.g. sheet closed right after a tap)
  — `mounted` only guards the `setState`s. Dropping the callback would
  silently lose a restock.
- Visual: progress bar colored by stock level, `stock / maxStock` label,
  spinner → green check after the write is queued.

### 5.3 persistStock (the write orchestration)

```dart
Future<void> persistStock(String size, int newStock) async {
  if (!mounted) return;                 // screen gone (sheet + screen closed)
  liveSizes[size] = newStock;
  final snapshot = Map<String, int>.from(liveSizes);
  final provider = Provider.of<ProductProvider>(context, listen: false);
  writeChain = writeChain.then((_) async {
    final saved = await provider.updateProduct(product['id'], {'sizes': snapshot});
    try {
      await ProductService.instance.syncProductActiveStatus(productId); // best-effort
    } catch (e) { debugPrint('Adjust Stock status sync failed: $e'); }
    if (saved) {
      _applyStockToLocalProduct(productId, snapshot);   // in-place grid update
    } else if (mounted) {
      debugPrint('Adjust Stock save FAILED for size $size ($newStock)');
      showSnackBar('Could not save stock. Please try again.');
    }
  });
}
```

- **`updateProduct` returns `bool`** — failures are now **loud** (SnackBar +
  log), never silent.
- `syncProductActiveStatus` is isolated in its own try/catch so a sync hiccup
  never turns a successful write into a reported failure.
- `_applyStockToLocalProduct` patches the grid's in-memory `inventory` so
  badges/filters update **without a full reload** (a reload would tear down
  the still-open editor sheet).

### 5.4 The write chain (end to end)

```
SellerInventoryRow.onStockChanged(newStock)     [800ms debounce, fires even if unmounted]
  └─ ManageProductsScreen.persistStock()         [mounted guard, liveSizes += full map]
      └─ ProductProvider.updateProduct(id, {'sizes': snapshot})   [returns bool]
          └─ SupabaseService.updateProduct(id, data)
              ├─ product column update ONLY if data has product keys
              │    (sizes-only ⇒ NO product SELECT — skipped to save a round trip)
              └─ _upsertInventory(id, sizes)
                  └─ inventory.upsert(rows, onConflict: 'product_id,size')  ← THE fix
                      └─ _syncVariantStock(id, rows)      [best-effort, never fails the write]
                          └─ distributeVariantStock() per size (pure helper)
                              └─ per-row product_variants.update({stock})
```

### 5.5 _upsertInventory — the 23505 story

`lib/services/supabase_service.dart`:

```dart
await _client
    .from('inventory')
    .upsert(rows, onConflict: 'product_id,size');
```

**This `onConflict` is load-bearing.** PostgREST resolves upsert conflicts via
the table's **primary key** by default. The live `inventory` table guards
`(product_id, size)` with a **UNIQUE constraint** (not the PK), so without
`onConflict` every restock attempted an INSERT and died with:

```
PostgrestException: duplicate key value violates unique constraint
"inventory_product_id_size_key" (code: 23505)
```

That single missing argument was the root cause of "restock didn't go through
the database." Every other composite-key upsert in the app already passed
`onConflict` explicitly (`device_tokens`, `store_follows`) — this one was the
odd one out. Now fixed.

### 5.6 _syncVariantStock — keeping variants honest

- Fetches that product's variant rows (best-effort: wrapped in try/catch so it
  can **never fail the authoritative inventory write**).
- Groups variants by size; for each inventory size, computes the delta between
  the current variant total and the new inventory total.
- `distributeVariantStock(currentStocks, target)` (pure helper in
  `lib/utils/product_stock.dart`) applies the delta row-by-row:
  - Positive deltas land on the first row.
  - Negative deltas drain rows, each clamped at 0, until absorbed.
  - No-op when totals already match (no DB writes issued).
- Per-row updates are individually try/caught — one row's failure doesn't
  abort the rest.

### 5.7 syncProductActiveStatus (auto-active)

`ProductService.syncProductActiveStatus(productId)`: if **any** inventory or
variant row has stock > 0 ⇒ `is_active = true`, else `false`. This is why
stocking out a product auto-hides it and restocking auto-reactivates it.

## 6. Other Writers of Stock (must not regress)

| Flow | Code | Effect on inventory/variants |
|------|------|------------------------------|
| Seller creates product | `ProductService.createProduct` → `_syncInventoryFromVariants` | inserts variants, then regenerates inventory from them |
| Seller edits product | `ProductService.updateProduct` → `_syncInventoryFromVariants` | deletes+re-inserts variants, then regenerates inventory (delete-then-insert clears stale rows) |
| Admin creates product | `SupabaseService.addProduct` | inserts product, `_upsertInventory(sizes)`, images. **No variants rows** ⇒ `_syncVariantStock` early-returns |
| Admin edits product | `SupabaseService.updateProduct` | product columns + `_upsertInventory(sizes)` if present |
| Online checkout | `createOrder` → DB triggers `decrement_inventory_on_order` | decrements `inventory` (SECURITY DEFINER, migration `20260711`) |
| POS sale | `createOrder(source: 'pos')` → `decrement_inventory_on_sale` | same, for in-person sales |
| Low-stock alerts | `_syncInventoryFromVariants` | fires `createLowStock` when any size ≤ 5 |

## 8. Gotchas & Known Risks

| # | Gotcha | Where | Notes |
|---|--------|-------|-------|
| 1 | **Live DB ≠ schema.sql for inventory PK** | schema vs DB | Live uses `UNIQUE (product_id, size)`; schema.sql documents `PRIMARY KEY`. Keep `onConflict: 'product_id,size'` — it works under either structure. Reconcile docs when convenient. |
| 2 | **`products.seller_id` can be NULL** | admin-created products | Admin portal inserts only `store_id`. Inventory/variants RLS require `products.seller_id = auth.uid()`, so a seller can't restock an admin-created product. Fix options: backfill `seller_id` or authorize inventory writes via `stores.owner_id`. |
| 3 | **RLS write failures are silent-ish** | `ProductProvider.updateProduct` | Now logged (`[ProductProvider] updateProduct failed for <id>: <e>`) and surfaced via SnackBar — never treat `false` as success. |
| 4 | **Debounce + screen teardown** | `persistStock` | If the whole screen is gone when the 800ms timer fires, the write is skipped (mounted guard). Intentional trade-off vs. calling `Provider.of` on a dead context. |
| 5 | **Stale timers from a closed sheet** | `SellerInventoryRow` | A row disposed by closing the sheet still fires once (by design). Rapid reopen of the same product inside the 800ms window could write the old sheet's snapshot — narrow window, accepted. |
| 6 | **Ordering of `writeChain`** | `persistStock` | Writes are serialized per `_showStockEditor` invocation. Each write carries the full map, so the final queued write always wins correctly. |
| 7 | **`hideOutOfStock` is client-side** | `fetchProducts` | Filtering happens in Dart after fetching all rows (`purchasableProducts`), not in SQL. Fine at current catalog sizes. |

## 10. Debugging Playbook (when a restock "doesn't save")

1. **Look for the failure log** — `[ProductProvider] updateProduct failed for <id>: <e>`.
   A `PostgrestException` with `code: 23505` = upsert conflict (onConflict missing — see §5.5).
   Any other `code` = likely RLS (`42501`) → check `products.seller_id` (§8, #2).
2. **Verify in SQL:**
   ```sql
   select id, name, store_id, seller_id from products where id = '<id>';
   select * from inventory where product_id = '<id>';
   select * from product_variants where product_id = '<id>';
   ```
   Inventory and variants per-size totals should match.
3. **No error at all?** Confirm the sheet was still open when the 800ms debounce
   fired, or check `persistStock`'s `mounted` guard (§8, #4).
4. **Saved but customer can't see it?** Confirm `inventory` has stock > 0 on at
   least one size AND `products.is_active` is true (`syncProductActiveStatus`
   handles this automatically after every Adjust Stock save).
